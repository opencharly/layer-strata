# 2026.292.1520 — fix(strata): pin the release tag without git emitting a not-a-commit warning

## Summary

Pins the upstream release **without** the warning git emits for an annotated tag, and keeps that
warning's text out of the shipped image label.

Two mechanisms, in this branch's two commits:

1. **`1ca3e47` — the pin.** The bed counted exactly one warning, and it was this:

   ```
   warning: refs/tags/v0.1.44.1 9791ea335ba2001c87b5f783146d6eb08fdd9e5e is not a commit!
   Note: switching to '296b59d2f73c8f04a805df29c2fa97655adace78'.
   ```

   `v0.1.44.1` upstream is an **annotated** tag: `9791ea3` is the tag object and `296b59d2` its peeled
   commit. `git clone --branch <tag>` hands git the tag object's oid, and `lookup_commit_or_die()`
   (git `commit.c:84-91`) warns that the oid it was given is not a commit before peeling it. The pin now
   clones the repo, fetches the tag ref (`git fetch --depth 1 origin refs/tags/<tag>`) and checks out
   `FETCH_HEAD`: the same peeled commit, with no such line.

2. **`5b8353d` — the comment.** Plan comments are baked into the `ai.opencharly.description` OCI label,
   so the explanatory comment that quoted the warning string put that string into the shipped artifact.
   The comment is now reworded and deliberately does not quote it. For **this** tree the emitted label
   carries the reworded comment and **zero** occurrences of the warning text (verified below).

**Review-round RCA (the missed control).** The previous body was headed with the superseded head
`1ca3e47` and its label claim was checked against that run's log, so the paste described an artifact
that was not the one shipping. The missed control is the head-in-fence discipline plus re-reading the
artifact the change actually reaches: a plan comment goes into the OCI label, so a comment-only commit
still changes the shipped image and re-invalidates its own bed. The root fixes here are (a) the paste
names the real head and backs it with per-file hashes of the bed's tree rather than an assertion,
(b) the label claim is re-measured on THIS run's log, and (c) the cache-hit ratio is stated as measured
instead of inferred as "cache-cold".

**One honest note, not a defect in this change.** After the bed exited (PASS, steps=14) the runner's
GPU housekeeping refused to restore the device:

```
preempt: could not set "nvidia-gpu" to vfio mode after releasing "check-strata-gpu-pod":

charly auto-preempts its own GPU pods; close these external GPU clients and retry
(refusing to force-unbind — would wedge the device_lock)
```

That is charly declining to force-unbind a device the operator's desktop holds — the designed behaviour,
printed after the bed had already passed, not counted in `warnings: 0` and with no effect on any phase.
