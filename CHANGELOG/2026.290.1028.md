# 2026.290.1028 — docs(strata): state the GPU bed's venue precondition in the bed itself

## Summary

States the GPU bed's **venue precondition** in the bed itself, and lands this repository's first change
through a PR.

`check-strata-gpu-pod` names a specific venue and never downloads: `GGUF_DIR: /gguf` binds
`~/.local/share/strata/gguf/IQ2_XS`, so the weights must already be staged. The ledger names that venue
(`cachyos-gpu-workstation-vm`: 64G / 12 cpu / 1T, RTX 40 → cuda arch 89). Measured: host `a` has the matching
**RTX 4080 SUPER** and an **empty store**, so it cannot run the bed. The note now sits beside the volume block,
because the roster comment *"run on demand"* otherwise reads as *"runnable anywhere"*.

**Disclosure — an anomaly I caused, recorded here rather than smoothed over.** This repository's `main` already
contains the cutover content, unreviewed. Cause: this repo was empty when I pushed `feat/strata` into it, and
`feat/strata` therefore became its default branch; the org's `bootstrap-repo-main.yml` then created `main` **from
the default branch**, so `main` and `feat/strata` pointed at the same commit (`b21c4089b25d`, verified by
`git rev-parse`). The bootstrap workflow's own header states that an empty repo cannot get its first `main` by any
operator path — I read that header *after* pushing instead of before. The missed control is mine: create the repo,
bootstrap `main`, **then** push. No force-push, revert, or branch game was used to hide it; this PR is how the work
reaches review, and the unreviewed state is disclosed to the reviewers rather than asserted away.

## Two known-reds: one filed, one now filed too (the review was right)

1. **`deploy-add` — filed as `opencharly/charly#968`.** The host prep hands the pod deploy plugin an
   **unqualified image ref** when the bed names its image by bare box name (`charly/charly/build_overlay.go:145-153`),
   so the alias step runs `podman tag strata <calver>` and fails with the venue's own words: `strata: image not
   known`. Corroborated on a second verb — `charly shell <registry-qualified ref>` fails the same way against an
   image that `podman images` lists. This blocks the bed's `deploy-add` → `config` → `check-live` stages.
2. **`check-image` — the nvidia gpgcheck check runs the PRE-fix command.** Mechanism established: `check box`
   executes the plan **baked into the image** (`ExtractMetadata → RunPlan`), and the image's
   `ai.opencharly.description` label carries the old awk-era command (`"stdout":` keys = 6, `old-awk = 1`,
   new wording = 0). Ten runs on host `a` could not dislodge it — tag invalidation, cleared git-ref cache, cleared
   `.view.` checkouts, both pins at the fix, content-hash bump — because every re-run **reused the image**
   (46–48 s, `cache=165/175`). `/charly-build:build` documents the class: *"a new tag, but the old content."*
   **Filed as `opencharly/charly#973`** after the first round's review correctly refused to let me park it as a
   "known-red". The lead it carries: the render/copy cache appears keyed on the candy's declared `version:` (the
   vendored dirs are `<candy>.<version>`), and a behaviour-only fix does not bump it — so the old plan survives
   every pin change, tag invalidation and cache clear.
