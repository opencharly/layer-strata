# 2026.292.1329 — feat(strata): serve from the bound store, and make the GPU bed prove it

## Summary

Makes the strata layer's service actually serve in a deployed container, and makes its GPU bed prove it.

The engine and the image were never the problem: the engine builds in-image (153/153 steps, stamp honest) and the server answers. What was broken was the deployment and the bed:

1. **The model store was never mounted.** `/data` was a named volume, empty on first start, so the entrypoint took its install path and died writing the read-only `/opt/strata/.venv` (`PermissionError: .strata-pip.json` → supervisord `FATAL` → nothing listened). The bed now binds the store and the shards via `charly config --bind <volume>=<path>` — the documented form; the earlier auto-path was a mis-invocation, tracked and retracted in charly#981.
2. **`/gguf` was bound to an empty directory.** The provisioned shards live in `models/IQ2_XS`, not `gguf/IQ2_XS`, so the engine started, answered `/health`, and reported `loaded: false` with `missing model shard` in its own log.
3. **The entrypoint wrote a symlink into the read-only image at launch** (`ln -sfn "$cfg" "$link"` → `Permission denied` → `FATAL`). The launch passes `--config "$cfg"` explicitly, so the invariant is now re-asserted only where the image allows it (`-w` on the parent dir), not suppressed.
4. **Three probes dialled the published port from inside the container.** `command:` runs via `podman exec`, so in-container probes use the container port; host-side `http:` steps keep `${HOST_PORT}`.
5. **The completion probe raced a 64 GB model load**; it now polls (`eventually`), and the two projection probes assert `/health` against the literals the bed declares instead of skipping on variables the check-var resolver does not see.

`stop_timeout` is declared as an integer because charly renders it verbatim into supervisord's integer `stopwaitsecs` (charly#978).

Two **image-dependency pin advances** are part of this diff and are behaviour-affecting:

6. **`candy/strata/charly.yml:51`** — `layer-cuda:v2026.289.1250` (`1796937a`) → `v2026.290.2137` (`d075bd36`, commit `73414650`). Without it the tree keeps resolving the pre-#12 nvidia layer, which is the CUDA header-root defect that blocked the whole effort.
7. **`charly.yml:31`** — `distro-cachyos:v2026.281.1001` → `v2026.290.2137` (commit `f0b8d029`), carrying the gpgcheck-guard fix that made the cachyos arm buildable at all.

**Correction to the Summary's framing:** an earlier revision of this body said "the engine and the image were never the problem". That is wrong as stated — the two pins above are image/composition corrections and belong to this change. What is accurate: the engine *binary* build and the image's Python environment were sound (153/153 compile steps, `imports OK`, `serve/server.py --help`); the **composition** around them was not, and these two pins plus the entrypoint/bed fixes are what made a deployed container serve.
