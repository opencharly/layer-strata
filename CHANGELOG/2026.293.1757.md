# 2026.293.1757 — docs(strata): document the surface for a model outside setup.py's menu (closes #9)

## Summary

Issue `#9` asked for a first-class external-model surface. The **surface** landed in the extra-args work — `STRATA_RUN_ARGS` (the `Layer C` argv merge), `STRATA_OVERLAY_JSON` (the `Layer B` volume overlay), and the config-ownership rule that keeps `args` out of the merge helper. What was never written down is **how a deployment actually uses it**. That is the gap this PR fills: documentation only, no image, candy or plan change.

### New README section: "Deploying a model outside the setup menu"

**1. The surface.** Why the run config's `args` is `SETUP_OWNED` and `STRATA_RUN_ARGS` is the sanctioned route (each named flag has its value replaced in place, or is appended when absent) — and that a hand-written config on the volume is *also* honoured, because the entrypoint seeds a baked config only when none exists and the install pass — the only place that would overwrite one — runs only when the config is absent or `REINSTALL=1`.

**2. The pack — and explicitly NOT our command.** The packing step is **upstream Strata's workflow, documented by upstream** (`docs/ORCA.md` in `Niko1221/Strata`); it uses the engine's own tool against the engine's pinned `gguf-py`, and `charly` neither wraps it nor ships it. This README does **not** reproduce its command — a non-INSTALL page may only tell a reader to run something that works with the `charly` binary alone. What stays here are the four rules that bite while following that workflow:

- do not borrow another model's `dense.bin` or `tokenizer/` — a pack exports its own tokenizer from its own GGUF;
- every split shard finished before packing, and `--native` / `--ple-gguf` both on **shard 1** because the PLE lookup table lives there;
- the compatibility conversion rounds relative to the GGUF's own dequantised weights — it does not recover the original checkpoint, and the pack records what it converted;
- it does not make an unsupported expert format work.

**3. MTP and the arena are separate budgets.** `--mtp` is optional (lookup-only drafting without it) and reusable across the same architecture, but acceptance must be measured. The **expert arena is system RAM** — tens of GiB free, ~50 GiB measured at IQ3 level — while VRAM only sets how much of the expert cache stays resident, so a smaller card is slower rather than unable to run.

The Configuration env list now names `STRATA_RUN_ARGS` and `STRATA_OVERLAY_JSON`; before, it folded them into "the engine's `STRATA_*` tuning variables".

### Deliberately not included

A concrete model's paths, pack name, quantisation or run config. This repo ships the **mechanism**; the deployment supplies the model. The deployment that prompted this — an Orca IQ3_XXS pack on a local pod — stays local by design, and the section says so explicitly.

## How tested

Documentation change. Every factual claim was checked against the shipped code rather than written from memory:

| claim | verified against |
|---|---|
| `args` is `SETUP_OWNED` | `candy/strata/charly-merge-config.py` — `SETUP_OWNED` contains `"args"` |
| seed-only-when-absent; install pass only when absent or `REINSTALL=1` | `candy/strata/charly-entrypoint.sh` (the `if [ ! -f "$cfg" ] && [ -f "$link" ]` seed, and the `if [ "${REINSTALL:-0}" = "1" ] \|\| [ ! -f "$cfg" ]` install guard) |
| `--base` copies `tokenizer/` and reuses `dense.bin` | `tools/iq_pack.py`'s `--base` help text and its `copytree(base/"tokenizer", …)` path |
| `--compat-bf16` "leaves experts and the PLE table unchanged" | the flag's own `--help` line, quoted rather than paraphrased |
| shard count / `--native`+`--ple-gguf` both on shard 1 | `docs/ORCA.md` in the Strata repo, which is what the workflow was walked end to end against |
| ~50 GiB arena | measured on the host during that walkthrough |

Two claims I removed while writing them, because the code does not support them: that `--compat-bf16` leaves attention weights and embeddings untouched (the flag's contract names only experts and the PLE table), and that the engine "resolves its siblings" from shard 1 (it reads shard 1; sibling resolution is not something I verified). Better a shorter doc than a confident wrong one.
